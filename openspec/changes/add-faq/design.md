# Design

## Context

- 首頁目前有三段：第一屏（含目錄「01 作品」「02 購買方式」）、`#works`、`#buy`。章節標題沿用 `.sec-head`（大號章節編號＋中文標題＋英文斜體），購買步驟用 `.steps`（上下細線的清單）
- 首頁 JSON-LD 寫在 `Pages/Index.cshtml`：一個 `@graph`，裡面有 Organization（`#organization`）與 WebSite（`#website`）。`PageSeo.Serialize` 會拿掉字典裡值是 `null` 的欄位，但陣列裡的 `null` 元素會照樣輸出
- 「購買方式」依「有沒有商品填了賣貨便連結」在「即將開賣」與「已開賣」兩種說法間切換；目前三件商品都沒有賣貨便連結
- 兩件上架商品都是棉線：泡芙小花提網（NT$450，尺寸未填）、花花杯墊（NT$200，長寬 10×高 3 cm）
- 測試用 `SiteFactory` 啟動整個網站，已有 `UseDatabase`、`UseSetting` 兩種「第一次 `Client()` 之前覆寫」的做法
- Google 只對政府、醫療網站顯示 FAQ 的搜尋結果樣式（2023-08 起）；FAQPage 對一般網站的價值是讓搜尋引擎與 AI 清楚知道哪段是問題、哪段是答案。真正會被引用的是頁面上看得到的文字

## Goals / Non-Goals

**Goals:**

- 頁面文字與結構化資料出自同一份資料，不會改了一邊忘了另一邊
- 測試不依賴真正的題目內容：答案還沒確認、之後改答案，測試都不用動

**Non-Goals:**

- 答案裡放連結或格式（粗體、清單）
- 後台編輯常見問題
- 其他頁面的結構化資料

## Decisions

### D1：放在首頁「03 常見問題」，全部展開

使用者決定放首頁（2026-10-19）。題目約 5 題，全部直接顯示，不用 `<details>` 收合：手機上不用一題一題點開；也和「商品頁不做頁籤」的決定一致（內容看得到就不藏起來）。

替代方案：

- 獨立頁面 `/faq`：要改頁首、頁尾導覽與 sitemap；題目少時一頁太空
- `<details>` 收合：搜尋引擎仍讀得到，但手機上要多點好幾次

### D2：題目放在程式裡的一份清單，透過 DI 提供給首頁

新增「常見問題」資料型別（題目、答案）與一份預設清單，啟動時註冊成服務；首頁的章節與 JSON-LD 都從這份清單產生。清單只放確認過的答案；還沒確認的草稿只記在本文件（見 D6）。

`SiteFactory` 新增「指定常見問題」的方法（和 `UseDatabase` 一樣在第一次 `Client()` 之前呼叫），測試放自己的題目，包括空清單與含 `</script>` 的答案。

替代方案：

- 寫在 `appsettings.json` 的 `Site` 區段：內容不是設定；設定檔的陣列按索引合併，測試很難把正式的題目清空
- 存資料庫、後台編輯：要加資料表、遷移與後台頁面，超出這次範圍。清單結構很單純，之後做後台第二階段時要搬進資料庫也容易
- 直接寫在 `Index.cshtml` 的 HTML 裡：JSON-LD 要再寫一次同樣的文字，容易不一致；也沒辦法測「沒有題目」

### D3：FAQPage 放進首頁同一個 `@graph`

```
@graph
├─ Organization  @id = {首頁}#organization   name、alternateName「JH Craft Studio」、url、logo、description、sameAs
├─ WebSite       @id = {首頁}#website        （不變）
└─ FAQPage       @id = {首頁}#faq            mainEntity：[ Question { name = 題目, acceptedAnswer: Answer { text = 答案 } } … ]
```

沒有題目時不放 FAQPage 節點。組 `@graph` 時用條件加入，不要放 `null` 進陣列（`WithoutNulls` 不會拿掉陣列裡的 `null` 元素）。

替代方案：輸出第二個 `<script type="application/ld+json">`：理由同 `add-site-name` 的 D1，`_Layout` 要改，影響所有頁面。

### D4：答案是純文字

頁面上用 Razor 輸出（自動跳脫），JSON-LD 的 `text` 放同一個字串，兩邊文字完全一樣。要引導訪客到 Instagram 或配色模擬器時用文字說明（例如「私訊 Instagram」），連結交給頁面上既有的按鈕。

替代方案：答案支援 Markdown（像商品故事）。可以放連結，但 JSON-LD 要另外產生純文字版本，兩邊就不完全一樣；目前的題目也用不到。

### D5：版面沿用編織誌

- 章節頭：`03`／「常見問題」／*FAQ*，和 01、02 同樣的 `.sec-head`
- 每一題：上下細線分隔；題號用藏青等寬字（`Q.01`），題目用粗體標題（`<h3>`），答案用一般內文。手機上題號、題目、答案由上往下排；桌機題目在左、答案在右，像雜誌的問答欄
- 目錄加「03 常見問題」；沒有題目時不列
- 不加新的動態效果；章節出現時的效果和其他章節一樣

### D6：題目與草稿答案（待貞貞確認）

## Risks / Trade-offs

- [開賣後第 4 題的「開賣前可以私訊 Instagram」過時] → 常見問題是固定文字，不會像「購買方式」自動切換。開賣（第一件商品填上賣貨便連結）時一起改這題；在 `docs/status.md` 的待辦記一筆
- [答案寫了不對的資訊（天數、運費）] → 只放貞貞確認過的答案；有變動時改清單、重新輸出
- [首頁變長] → 5 題純文字，估計手機上多 1～2 屏（實作後實際量），放在最後面，不影響第一屏與作品。上線前用 390px 手機實際捲動檢查
- [AI 搜尋不一定引用] → 這是外部服務的判斷；我們能做的是把問答文字寫清楚，並確認 Bing 與 Google 都收錄了首頁

## Migration Plan

1. 把 D6 的訊息傳給貞貞
2. 實作章節、JSON-LD、別名與測試（測試用自己的題目，不用等答案），`dotnet test` 通過
3. 收到答案後放進清單：只放確認過的題目
4. 390px 手機實際操作檢查首頁（目錄跳轉、閱讀、沒有水平捲軸）
5. commit、push，執行 `bash tools/deploy-pages.sh`
6. 用 Schema Markup Validator 檢查 `https://jhcraftstudio.com/`：Organization（含別名）、WebSite、FAQPage 都被讀到，沒有錯誤
7. Search Console 與 Bing Webmaster Tools 對首頁重新要求建立索引

步驟 3 之前若要先部署（例如只上別名），清單維持空的，首頁不會出現章節。

回復：revert 這次的 commit 再部署一次。
